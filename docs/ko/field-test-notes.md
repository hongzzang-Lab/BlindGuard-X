# BlindGuard-X 실물(공원) 테스트 키트 v2

**무엇을 확인하나**
1. **포스터의 Vision 구조가 실제 웹캠 + Pi 5에서 돌아가는지**
   - Cam1: Optical Flow + Track Memory → Adaptive ROI + ROI Packing → YOLO26n-NCNN(416) → ByteTrack → Homography
   - Cam2: Polygon ROI → MOG2 → Sparse LK → 경계 접근 → EMR
   - 단계별 처리 시간, 검출, 추적 ID, 위치 오차를 잰다.
2. **차량 역할 팀원(폰 앱 GPS) 쪽으로 보행자 역할 팀원이 건너면, 그 폰 앱에 경고가 실제로 뜨는지** (End-to-End, 지연까지)
3. **모든 결과를 노트북에 저장**
   - 서버 기록은 실시간으로 노트북에 쌓인다.
   - Pi 기록과 오버레이 영상은 `tools/sync_pi.sh`로 가져온다.

```
 [웹캠 Cam1 횡단보도]──┐                                             ┌──▶ 폰 A 앱 (차량 역할)
                      ├─ Pi 5: pi/edge.py ──Wi-Fi──▶ 노트북: server/exp_server.py ◀── 폰 A GPS (1초마다)
 [웹캠 Cam2 대기구역]──┘   보행자 위치·속도            · GPS→바닥좌표, 맵매칭+칼만
                          Cam2 EMR·이벤트              · 차량별 CPA → 경고(주의/경고/긴급)
                          오버레이 녹화                · 조작 페이지 http://10.42.0.1:8000/control
                                                       · 기록 logs/server_<시각>/
```

### 화면 두 개
| 주소 | 용도 |
|---|---|
| `http://<노트북IP>:8000/control` | **조작 페이지**: 시험 시작·종료, 보정, GPS 기준점, Cam1 모드 바꾸기 |
| `http://<노트북IP>:8000/monitor` | **중앙 관제 화면** (데모 영상용): Cam1·Cam2 실시간 결과 화면, 차량 GPS·보행자 지도, 앱으로 보낸 경고(원문 포함), 사건 로그, 지연(촬영→서버, 판정→전송, 서버→폰) |

노트북 화면 하나에 관제 화면을 띄우고, 다른 창이나 다른 기기에서 조작 페이지를 쓰면 편하다. 관제 화면은 읽기 전용이다.

### 남길 영상 3가지와 이 키트의 대응
| 영상 | 무엇으로 | 결과물 |
|---|---|---|
| ① Cam1 비전 성능 (실제 상황) | V1 실험 (+ H0) | Pi `video/T###_V1_cam1_overlay.avi`: ROI·Packing 캔버스·트랙 ID·바닥 좌표·단계별 ms가 그려진 영상. 원본 `_raw.avi`로 4가지 모드 재분석 |
| ② Cam2 비전 | V2 실험 | Pi `video/T###_V2_cam2_overlay.avi`: 대기구역·경계선·발 위치·LK 흐름·EMR 막대·이벤트 |
| ③ 최종 데모 | C1 실험 + **관제 화면 녹화** | 노트북 화면 녹화(관제 화면) + 폰 A 화면 녹화(안드로이드 '화면 녹화') + 현장 촬영. 서버 로그에 경고별 지연이 남음 |

- 노트북 화면 녹화: 우분투 `Print Screen` → 녹화 버튼, 또는 OBS / SimpleScreenRecorder (`sudo apt install simplescreenrecorder`).
- 서버 터미널에도 경고마다 지연이 한 줄씩 찍힌다.
  - `[경고] 차량 A None→warning … 촬영→서버 48 ms · 판정→전송 2 ms`
  - `[수신] 폰 A seq 12 서버→폰 31 ms`
- 같은 값이 `alerts.csv`와 `alert_acks.csv`에도 남는다.

## 1. 준비물
- Pi 5 + 쿨러, **5V 5A(PD 27W) 보조배터리**
  - 3A짜리면 USB 전류가 부족해서 웹캠이 끊길 수 있다. 9장 '문제 해결' 참고.
- USB 웹캠 2대, 삼각대 또는 스탠드 2개 (2 m 이상), 연장 USB 케이블, 테이프·고정끈
- 노트북 (충전), 폰 A (앱 설치, 충전), 다른 폰 1대 (60fps 촬영용, 선택)
- 줄자 (20 m 이상), 바닥 표시용 테이프·분필, 콘 4~6개
- 조작용 이어폰 또는 스피커 (출발 신호음)

## 2. 현장 배치 (바닥 좌표, m)

```
 y
 +2  ─ 인도 ─────────────────────────────────────────────────────   ← Cam2 가 대기구역을 봄
 +1  ─ ─ 대기선 (보행자 B 서는 곳) ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─
  0  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━ 연석선 (빨간 테이프) ━━━━━━━━━━━   ← x 축
 -1.75 ─ ─ 차로 중심선: 차량 A가 걷는/달리는 선  → (+x 방향) ─ ─ ─ ─
 -4   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
      S(-30)        콘(-6/-11)   정지선(-2)  |횡단보도 x=-1.5~+1.5|   +5     +15
```
- **좌표 약속**: 연석선 위에서 **인도를 왼쪽**에 두고 바라보는 방향이 +x다. 반대로 정하면 GPS와 카메라 좌표가 거울처럼 뒤집힌다.
- 공원 산책로 한쪽 가장자리를 '연석선'으로 정한다. 차량 역할(A)은 그 선에서 1.75 m 떨어진 선을 따라 움직인다.
- **Cam1**: 횡단보도 주변(대략 x −4~+4, y −5~+2)이 다 보이게 2 m 이상 높이에서 비스듬히 내려다본다. 사람 발끝까지 화면에 들어와야 한다.
- **Cam2**: 대기구역(인도 쪽, 연석선 근처)을 옆이나 뒤에서 본다. 나무·풀이 덜 나오게 바닥 위주로 잡는다.
- 카메라는 보정 뒤에 절대 움직이지 않게 고정한다.
- 현장 크기가 다르면 `site.json`의 `floor.lane_y`와 `crosswalk_x`를 고친다.

## 3. 네트워크·실행 순서 (현장, 10분)

1. **노트북 핫스팟**: `bash tools/hotspot_laptop.sh` (이름 BGX-TEST / 비밀번호 <비밀번호>, 노트북 = 10.42.0.1)
2. **Pi 연결**: `sudo nmcli dev wifi connect BGX-TEST password <비밀번호>`
   - 미리 집에서 한 번 해 두면 자동으로 붙는다.
   - Pi 주소는 노트북에서 `ip neigh`로 확인한다.
3. **폰 A 연결**
   - Wi-Fi BGX-TEST에 연결한다. '인터넷 없음' 경고가 떠도 **연결 유지**를 누른다.
   - **모바일 데이터를 끈다.** 켜 두면 폰이 노트북 대신 LTE로 나가려 해서 서버에 못 붙는다.
   - GPS는 데이터 없이도 된다. 다만 첫 위치를 잡는 데 1~2분 걸릴 수 있으니 앱을 미리 켜 두고 하늘이 트인 곳에 둔다.
4. **서버**: `bash tools/start_server.sh` → 브라우저에서 `http://localhost:8000/control` 열기
5. **Pi**: `source ~/bgx-venv/bin/activate && cd ~/realtest && python3 pi/edge.py`
   - 화면 상단에 `Pi 연결`(초록)이 뜨면 연결된 것이다.
6. **폰 A**: 앱 실행 → '주행 시작'. 조작 페이지 '연결된 폰' 표에서 **차량 A, 주행 예**가 보여야 한다.

## 4. 보정 (조작 페이지 ③탭, 30~40분)

### 4-1. Cam1 바닥 보정 (Homography)
1. 바닥에 테이프 점을 붙이고 줄자로 좌표를 잰다.
   - **보정용 6~8점**: 화면 네 귀퉁이 근처와 가운데에 넓게. 예: (−3, 1.5) (3, 1.5) (−3, −4) (3, −4) (0, 0) (0, −1.75)
   - **검증용 3~4점**: 보정용과 다른 위치. 예: (−1.5, 0.5) (1.5, −1) (0, −3)
2. **📷 사진 찍기** → 사진에서 테이프 점을 클릭하고, 표에 x, y를 입력한다. 검증점은 '용도'를 **검증**으로 바꾼다.
3. **계산**을 누른다.
   - 사진에 1 m 격자가 겹쳐 보인다. **빨간 선(연석선)이 실제 테이프 위**에 있어야 한다.
   - 검증점 평균 오차를 기록한다. 0.2 m 안팎이면 좋다 (시뮬 실측 0.203 m).
4. **Pi에 적용**. ②탭 Cam1 화면의 빨간 선이 테이프와 맞는지 다시 확인한다.

### 4-2. Cam2 대기구역
1. 📷 사진 → **구역 꼭짓점** 모드로 대기구역 꼭짓점을 차례로 클릭한다.
2. **경계선 2점** 모드로 바꾸고, 차도-인도 경계 양 끝을 클릭한다.
3. **Pi에 적용** → 배경을 새로 학습하므로 **3~4초 동안 구역을 비운다**. ②탭 상단에 'BG LEARNING'이 사라지면 끝난 것이다.

### 4-3. GPS 기준점 (폰 A 좌표 → 바닥 좌표)
1. 폰 A(앱 켠 상태)를 **p0 = (0, −1.75)**, 즉 차로선과 횡단보도 가운데에 놓는다. **기록 시작 → 30초 → 기록 끝**.
2. **p1 = (−20, −1.75)**, 즉 차로선을 따라 20 m 뒤에서 똑같이 한다.
3. **기준점 계산**을 누른다.
   - 창에 'GPS로 잰 두 점 거리 vs 실제 20 m'가 나온다. 차이가 GPS 품질 지표다.
4. **치우침 보정** (시험 사이 20~30분마다, 선택): 폰을 출발점 S(−30, −1.75)에 30초 놓고 기록하면, 그 시각의 GPS 치우침을 빼 준다.

> 같은 폰으로 바로 전에 기준점을 잡기 때문에 GPS의 느린 치우침이 같이 빠진다. 팀의 10/20 실측에서도 오차가 몇 분씩 같은 방향으로 이어졌다.
> 서버는 차량이 차로 위를 달린다고 보고 **y를 차로선에 맞추고(맵 매칭) 차로 방향으로 칼만 필터**를 쓴다. 핸드오프 설계의 '칼만 → 맵 매칭'과 같은 구조다.

## 5. 실험별 진행 (①탭) — 약 3시간

공통 조작
- 실험·라벨을 고르고 **Space = 시작/종료**, **M = 이상한 순간 표시**. 종료할 때 결과 메모를 적는다.
- 시험을 시작하면 Pi가 **그 시험만 오버레이 영상으로 녹화**한다 (`T005_V1_cam1_overlay.avi` 등).
- 역할은 **조작자**(노트북), **차량 A**(폰), **보행자 B** 셋이다. 촬영자가 있으면 60fps로 폰 A 화면과 B를 같이 찍는다.

### H0 · 바닥 보정 확인 (10분)
- 검증용 테이프 점 위에 B가 5초씩 서 있는다. 라벨은 `x=1.5,y=-1`처럼 그 점 좌표다.
- 지표: 사람 발 위치 오차 P50/P95, 검출률.

### V1 · Cam1 비전 파이프라인 (40분) — "포스터 구조가 실제로 도는가"
- ②탭에서 모드를 고른다: **FULL / FIXED / ADAPTIVE / PACKED(포스터)**.
- ADAPTIVE·PACKED에는 **YOLO 실행 방식**이 두 가지 있다.
  - **필요할 때만 (기본)**: 사이 프레임은 트랙 상자 안의 특징점을 Sparse LK로 따라간다. YOLO는 아래 경우에만 돈다.
    - 새 움직임이 기존 트랙 밖에서 생겼을 때
    - 추적 점을 잃었을 때
    - 최소 3프레임에 한 번
    - 전체 스캔 차례일 때
  - **매 프레임**: 포스터 실측 방식이다.
  - 두 방식의 FPS와 검출, 'YOLO 실행률'을 비교한다. 화면과 관제 화면에 실행률이 표시된다.
- 같은 동작을 모드마다 반복한다. 시험 하나는 20~30초.

| 동작 (라벨) | 내용 | 반복 |
|---|---|---|
| `1명_횡단` | B가 대기선에서 반대편까지 건넘 | 모드마다 3회 |
| `2명_교차` | 두 사람이 횡단보도에서 엇갈림 | 모드마다 2회 |
| `원거리_정지` | 화면 먼 쪽(y≈−4)에 10초 서 있음 | 모드마다 1회 |
| `빈화면` | 아무도 없음 15초 (추론 생략 확인) | PACKED·FULL 각 1회 |

- '원본 영상도 녹화'가 V1에서는 자동으로 켜진다. 나중에 **같은 영상으로 4가지 모드를 공정하게 비교**할 수 있다 (6장).
- 지표 (자동): 단계별 시간 P50/P95, 전체 화면 스캔·추론 생략 비율, ROI 수, Packing 배율, 검출률, 고유 ID 수, 촬영→서버 지연, 온도.
- 비교 기준: 시뮬 실측 YOLO 26.2~28.0 ms, Cam1 9.3~9.8 FPS, ROI 비교표 (FIXED 31.8 / ADAPTIVE 21.1 / PACKED 15.4 FPS).

### V2 · Cam2 대기구역 (30분)
- 시작 전에 구역을 비우고 ②탭 **배경 다시 학습**을 누른다.

| 라벨 | 동작 | 반복 |
|---|---|---|
| `wait` | 대기구역에 20초 가만히 서 있기 | 5회 |
| `sway` | 서성이기·몸 돌리기·한 발 앞뒤 (경계선은 안 넘음) | 5회 |
| `depart` | 5초 대기 → 경계선을 넘어 차도 쪽으로 출발 | 8회 |

- 판정 (자동)
  - depart에서 **emr_high가 cross(경계 넘음)보다 먼저** 나오면 성공이다. 그 시간차가 **선행 시간**이다.
  - wait/sway에서 emr_high가 나오면 **오탐**이다.
- **EMR 식은 [임시]**(근접 0.4 + 차도 방향 0.4 + 지속성 0.2, 기준 0.7)다. 위험 판정(CPA)에는 합치지 않는다.

### G0 · GPS 정지 오차 (10분, 선택)
- 폰 A를 알고 있는 점(예: `x=-10,y=-1.75`)에 60초 둔다. 앱은 '주행 시작' 상태여야 한다.
- 지표: GPS 원본 오차 vs 맵 매칭 후 오차.

### C1 · 충돌 경고 End-to-End (60~80분)
**안전 규칙**
- A는 경고가 오면 멈춘다. **안 와도 정지선 x=−2에서 반드시 멈춘다.**
- 뛰는 대신 빠른 걸음이나 자전거(천천히)도 괜찮다.
- 주변 시민 동선을 피한다.

| 시나리오 | 차량 A (폰) | 보행자 B | 기대 |
|---|---|---|---|
| R1_상충 | S(−30)에서 '삐'에 출발, 차로선 따라 | A가 **출발 신호 콘**을 지날 때 횡단 시작 | **A에 경고** |
| R2_통과후횡단 | R1과 같음 | A가 x=+5를 지난 뒤 횡단 | 경고 없음 |
| R3_대기만 | R1과 같음 | 대기선에서 서성임만 | 경고 없음 |
| R4_반대방향 | x=+5에서 '삐'에 +x로 멀어짐 | '삐' 2초 뒤 횡단 | 경고 없음 |

- **출발 신호 콘 위치** = 2.5초 × A 속도: 빠른 걸음(1.8 m/s) → x=−4.5, 뛰기(2.8 m/s) → x=−7, 자전거(4.5 m/s) → x=−11. 라벨에 속도 종류를 적는다.
- **반복**: R1 8회, R2·R3·R4 각 5회. 순서를 섞는다 (R1→R3→R1→R2→R4→R1…).
- 카운트다운 3초 '삐-삐-삐-삐이'에 A가 출발한다.
- 폰 A 화면에 배너가 뜨고 음성이 나오는 것은 사람이 확인하고, 이상하면 M 키로 표시한다.
- **60fps 촬영**(R1 몇 회): B의 첫 발과 폰 A 화면이 한 화면에 나오게 찍는다. 프레임을 세어 '보행자 출발 → 폰 화면 경고'의 진짜 반응 시간을 구한다.
- 지표 (자동)
  - 위험 감지 성공률, 오경고율
  - **정지선까지 남은 시간**: 첫 경고 순간 A의 위치·속도로 계산한, 정지선(x=−2)까지 남은 시간. A가 경고를 받고 멈춰도 계산된다
  - **보행자 진입 전 시간**: 경고부터 B가 연석선을 넘을 때까지
  - 전달 지연: 촬영→서버→판정→전송→폰 수신
  - GPS 정확도, **GPS와 카메라의 차이** (A도 Cam1에 찍히면 '차량 본인' 트랙과의 거리)
- **차량 본인 제외**: A도 Cam1에 사람으로 찍힌다. 서버는 GPS 위치 근처에서 속도가 비슷한 트랙을 '차량 본인'으로 보고 판정에서 뺀다. 지도에서 A의 점을 클릭해 직접 지정해도 된다.

**GPS가 너무 나쁠 때 (예비)**: '차량 위치 출처'를 바꿔서 같은 시험을 반복한다. 각 결과에는 출처가 같이 기록된다.
- **카메라 트랙 지정**: 지도에서 A의 점을 클릭한다. Cam1이 A의 위치를 재고, 경고는 여전히 폰 A로 간다.
- **가상 차량**: 시나리오 `V_S1_가상상충`, `V_S3_가상대기만`을 쓴다.

## 7. 지표 정의
- **단계 시간**: Pi 안에서 `time.perf_counter`로 잰 Flow, ROI, Pack, YOLO, Track, Homo, 전체 (ms). 프레임별로 기록하고 P50/P95로 보고한다.
- **촬영→서버**: 프레임을 받은 시각(Pi)부터 서버 도착까지. Pi와 서버의 시계 차이는 2초마다 자동으로 맞춘다 (왕복 시간의 절반 방식).
- **서버→폰**: 앱이 받은 즉시 보낸 `alert_ack` 시각(폰 시계를 ping으로 서버 시계에 맞춤) − 서버 전송 시각.
- **위험 감지 성공률** = 성공 / (성공 + 놓침), 경고가 나와야 하는 시험 기준.
- **오경고율** = 오경고 / (오경고 + 정상), 경고가 나오면 안 되는 시험 기준.
- **경고 단계**: dCPA ≤ 2 m 이고 0 ≤ tCPA ≤ 3 s일 때 경고하고, tCPA ≤ 1 s면 긴급, ≤ 2 s면 경고, ≤ 3 s면 주의 **[임시]**. 단계는 1초 동안 유지한다.

## 8. 모의 실행 기대치 (`tools/simulate_gps.py`, 서버와 같은 코드, 각 40회)
R1은 정지선 전에 경고가 나온 비율, R2~R4는 경고가 나온 비율(오경고)이다. 맵 매칭 + 칼만은 켬(서버 기본).

| GPS (남은 치우침 σb / 흔들림 σw) | 차량 속도 | R1 | R2 | R3 | R4 |
|---|---|---|---|---|---|
| 좋음 1 m / 1 m | 빠른걸음 1.8 m/s | 100% | 0% | 90% | 0% |
| 좋음 1 m / 1 m | 뛰기 2.8 m/s | 100% | 0% | 100% | 0% |
| 보통 2 m / 2 m | 뛰기 2.8 m/s | 98% | 0% | 100% | 0% |
| 나쁨 4 m / 3 m | 빠른걸음 1.8 m/s | 55% | 12% | 85% | 2% |
| 나쁨 4 m / 3 m | 뛰기 2.8 m/s | 78% | 2% | 78% | 0% |
| 나쁨 4 m / 3 m | 자전거 4.5 m/s | 95% | 2% | 80% | 0% |

- **맵 매칭을 끄면** R2 오경고가 60~80%로 늘어난다. 차로 위라는 정보가 핵심이다.
- **R1 여유**는 정지선 전 0.6~1.3초 정도다 (보행자가 출발 신호 콘에서 출발하는 설계 때문). 속도가 빠를수록 여유가 크다.
- **R3(서성임)**은 CPA의 등속 가정 때문에 오경고가 많이 나올 것으로 예상된다. 대기 중 몸 흔들림을 '차도 쪽으로 걷기'로 늘여 예측하기 때문이다. 이 결과는 **Cam2(EMR)를 판정에 합쳐야 하는 이유**를 보여 주는 근거가 된다. 결과가 나빠도 고치지 말고 그대로 기록한다.
- 이 표는 가정한 GPS 모델로 낸 값이라 실제와 다를 수 있다.

## 9. 문제 해결
| 증상 | 해결 |
|---|---|
| 조작 페이지 'Pi 없음' | Pi가 핫스팟에 붙었는지(`nmcli`), `site.json`의 `server_url`(10.42.0.1), 노트북 방화벽(`sudo ufw allow 8000`) |
| 폰이 연결 안 됨 ('연결된 폰' 비어 있음) | 모바일 데이터 끄기, Wi-Fi '연결 유지', 앱을 `--dart-define=SERVER_URL=...`로 빌드했는지 |
| '주행 중: 아니오' | 앱에서 '주행 시작'. 앱은 GPS와 서버 둘 다 연결돼야 시작 버튼이 켜짐 |
| 보조배터리에서 웹캠이 끊김·안 열림 | 5V 5A 배터리를 쓴다. 아니면 Pi `/boot/firmware/config.txt`에 `usb_max_current_enable=1` 추가 후 재부팅 (전류가 부족하면 Pi가 꺼질 수 있으니 주의) |
| Cam1 '보정 필요' | ③탭 Cam1 보정 → Pi에 적용 |
| 파란 점 위치가 실제와 다름 | 카메라가 움직였으면 다시 보정. 빨간 선이 테이프에서 벗어났는지 ②탭에서 확인 |
| 경고가 서버 표에는 있는데 폰에 안 뜸 | 폰이 '차량 A'로 붙었는지, 주행 중인지, 앱 음량 |
| GPS ±값이 15 m 이상 | 하늘이 트인 곳으로 옮기고 1~2분 기다리기. 기준점을 다시 잡기. 그래도 나쁘면 5장 예비 방법 |
| 온도 75°C 이상, FPS 떨어짐 | 그늘·쿨러, 시험 사이 휴식. 결과 메모에 적기 |
| Cam2 '사람'이 계속 뜸 (빈 구역인데) | 그림자·바람 → ②탭 '배경 다시 학습', 구역을 바닥 위주로 다시 지정 |

## 10. 발표 질의응답에서 그대로 말할 것
- **실측한 것**
  - USB 웹캠 2대 → Pi 5 실시간 처리 (포스터 Cam1·Cam2 구조, 단계별 시간)
  - 보행자 바닥 위치·속도
  - 폰 GPS 차량 위치 (맵 매칭 + 칼만)
  - 차량별 CPA 판정, 실제 앱 수신·표시, 구간별 지연
- **차량은 사람이 폰을 들고 걷거나 뛰어서 흉내** 냈다. 실제 차량 속도·GPS 조건과는 다르다.
- **아직 안 한 것**
  - Cam2 결과를 위험 판정에 합치기 (EMR 식 미확정)
  - 보행 신호 상태 합치기
  - 야간 조건
- **위험 단계 기준**(tCPA 1/2/3 s)과 EMR 가중치는 [임시]이다.
- **ROI 비교**: V1에서 같은 장면, 같은 Pi로 네 모드를 잰 표를 근거로 답한다.
